## 1. サービス概要

**このサービスはどんなサービスか**

tsundokuは、書籍を積みがちな人が、積んでいる本の量を知って買う手を止め、「読んだ」を積み上げられるようになるサービスです。
本のタイトルと状態（積んでる／読んでる／読んだ）だけをシンプルに登録し、一覧で見られます。
読書の記録や共有ではなく、書籍コレクターが抜け出すことに特化しています。

**誰の、どんな課題を、どう解決するか**

- **誰の**：仕事と家庭で学習時間が限られ、焦りや金銭的な余裕から本を買い足してしまう30代の書籍コレクター（まずは同じスクールの受講生）
- **どんな課題を**：買うことで満足し、読み切れない本が積み上がって、義務感で学習意欲が下がってしまうこと
- **どう解決するか**：本の状態を登録して一覧にすることで、新しい本を買う直前に、積んでいる量が目に入るようにする

---

## 2. このアイデアはどこから生まれたか

### 2-1. きっかけとなった体験・感情

プログラミング学習を始めてから書籍を買い漁り、読めていない本が溜まって「書籍コレクター」になっていた。主にKindleで読んでいるが、どこを読んで、どこを読んでいないかがわからなくなり、読むことをやめてしまった経験がある。

### 2-2. なぜそれが「気になった」のか

書籍は無料ではなく、高すぎることはないが安すぎるわけでもない。そのため「もったいないことをした」という気持ちが強い。一度見切りをつけると再び読む気力が湧かず、せっかく買った本を積んでしまい、書籍コレクターになる。

---

## 3. 課題の整理

### 3-1. 表に見えている困りごと

目次から任意のページだけ読んだのか、最初から続けて読んだのかが、時間が経つとわからなくなる。書籍は体系的に学べる教材であり、飛ばし読みも自由だと考えているが、特に初学者は前提知識が足りないため、最初から読むほうが望ましいとも思っている。「読んだつもり」でも「どこを読んだっけ？」とモヤモヤし、本を活かしきれていない気持ちになる。

### 3-2. 本当に解決したい課題

「なぜ困るのか？」を3回掘り下げた。

| 回 | なぜ困る？ | 答え |
| --- | --- | --- |
| 1 | 読んだ範囲があやふやだと | 積んでいるのか読んでいるのかわからず、読む必要性が見えなくなる |
| 2 | 読む必要性が見えないと | 後回しにして忘れ、別の本を買ってしまう（書籍コレクター） |
| 3 | 忘れて買い足すと | 読まなきゃという義務感だけが増え、消化できずに読む意欲が薄れる |

**本当に解決したい課題**

> 初学者は「何を読むべきか」を取捨選択できないまま本を買い足してしまい、読み切れない本への義務感で学習意欲が下がってしまう。

## 4. 想定ユーザーについて

### 4-1. 想定しているユーザー

> 仕事と家庭があり、学習時間が限られている30代。プログラミング学習を始めたばかりで、焦りと社会人経験の長さからくる金銭的な余裕から本を買い足し、「買って満足」してしまう書籍コレクター。

| 項目 | 設定 | 理由 |
| --- | --- | --- |
| 年齢 | 30代 | 社会人経験を積んでいるぶん失敗を恐れやすく、「誰よりも頑張らなきゃ」という気持ちが先行する。金銭的な余裕も出てくるため、お金にものを言わせて本を買い、買うことで満足してしまう |
| 生活・状況 | 仕事と家庭があり、学習時間があまり取れない。パフォーマンスを上げなきゃと焦っている | 買って満足するが、時間がないので消化できない。本の状態を可視化することで、積んでいる量を認識できる |
| 環境 | Kindleでも紙の本でも読む | 媒体を問わず、タイトルと状態だけで管理できる |

### 4-2. 自分とユーザーの距離

**自分自身。** いまもKindleで読んでいる本を全部は読めておらず、積んでいる状態。読む時間があまり取れないのに、持っている本が多い。

### 4-3. 実際に使われる可能性について

- **最初に使ってくれそうな人**：同じスクールの受講生
- **思い出す場面**：積んでいる本があるにもかかわらず、新しい本を買おうとしているとき
- **いまの代わり**：Kindleの読書位置の強調表示。ただし何度も動かすため、どこからどこまで読んだかがわからなくなる
- **置き換えてまで使う理由**：書籍コレクターから抜け出すには、読むための計画が必要で、そのためにはまず積んでいる本が何冊あるかを自分で認識する必要がある。このアプリで可視化することで、冊数を把握し、消化の計画を考える後押しになる

> ※「周りの受講生も同じ悩みを感じているか」は、現時点では想定。リリース後に確かめる（8. 懸念点4を参照）。

### 4-4. 導入・継続の流れ

1. **きっかけ**：自分が書籍コレクターだと自覚している人が、このアプリを知って使う（使うことで、積んでいる本の多さに気づく）
2. **最初の一歩**：アカウント登録と書籍の登録。登録はタイトルと状態だけなので、負担は少ない
3. **続ける理由**：書籍コレクターから抜け出すために必要だから。積んでいる本の多さに気づくと、新しい本を買うことが一旦なくなる。「読んだ」の基準（1ページ目から全部読むかどうか）や、消化し終えたあとに新しい本を買うかどうかは、個人に任せる

## 5. 既存サービス・競合調査

### 5-1. 似たサービス

| サービス | どんなことができるか |
| --- | --- |
| 読書メーター | 読んだページ数や冊数をグラフで記録・管理でき、ほかの読書家と交流できる。「読んだ本」「読んでいる本」「積読本」「読みたい本」の状態を登録できる |
| ブクログ | 本や電子書籍（Kindle）の管理、読書状況の設定、5段階評価、レビューの登録ができる。本棚の見た目が良い |
| 読書管理ビブリア | 機能を絞った、軽い読書記録アプリ |

> ※上記は比較記事をもとにした情報、公式サイトの確認は実施済み。実際に触って、積読の扱いや使い心地を確かめる（要確認）。

### 5-2. それでも自分が作りたい理由

- **読書メーター**は習慣化と共有に寄ったサービス。ページ数や冊数のグラフ化もその一環で、習慣化や他人との共有は、tsundokuが目指すものではない。
- **ブクログ**は、お気に入りの本棚、共有によるレビュー、読書管理ができる。読書そのものが好きで、読書を通じて他人と関わりたい人向けのサービス。
- tsundokuは、読書好きや交流のためではなく、**書籍コレクターがそこから抜け出すためのアプリ**。

### 5-3. 差別化を「体験価値」で表現する

> 積んでいる本が何冊もあるのに、また新しい本を買おうとしている書籍コレクターの、**買う直前の瞬間**を一番助けるアプリ

## 6. このサービスで提供したい価値

### 6-1. ユーザーの変化

| 観点 | 変化 |
| --- | --- |
| 行動 | 読み終えていない本があるのに、新しい本を買うことがなくなる（アプリが禁止するのではなく、冊数が見えることで自然とそうなる） |
| 気持ち | 積んでいる本が見えることで、消化のゴールが明確になる（漠然とした義務感が、数えられる目標に変わる） |
| 考え方 | 本は買うことや集めることが目的ではなく、読むことでしか自分の力にならないと知る |

### 6-2. 価値を一文で表す

> このサービスは、書籍を積みがちな人が、積んでいる本の量を知って買う手を止め、「読んだ」を積み上げられるようになるサービス

## 7. このアプリで実現すること

### MVPで作る機能

1. アカウント登録
2. 本を1冊ずつ登録（タイトル＋状態：積んでる／読んでる／読んだ）
3. 登録した本の一覧表示

※積んでいる本は何十冊も想定せず、1ページで見られる数を前提とする。

### 本リリースで作る機能

- 積んでいる冊数のカウント
- 状態での絞り込み
- 手持ちの本をまとめて登録する機能

### 作らないと決めたこと

既存サービスに近づいてしまうため、次の機能は実装しない。

- 消化の計画を立てる後押し
- 「何のために買うか」を考えるきっかけ
- 本の中の読書位置の記録（「どこまで読んだか」。3-1の困りごとは、このアプリでは解決しない。tsundokuが扱うのは、1冊の中の進み具合ではなく、本ごとの状態）

## 8. このアプリの懸念点とその対策

### 懸念1：蔵書が想定より多く、1ページに収まらない

- **なぜそう思うか**：3-2で「集めた書籍はかなりの数になる」可能性を否定し切れない、MVPの「1ページで見える」前提が崩れる可能性がある
- **対策**：書籍コレクターが実際にどれだけ積んでいるかは、運用してレビューを受けないとわからない。最低限の設計にとどめてリリースを早めることを最優先にし、必要になったら数十冊ある場合の表示方法を検討する

### 懸念2：手持ちの本が多い人ほど、最初の登録が重く感じる

- **なぜそう思うか**：MVPは1冊ずつ登録なので、50冊なら50回の入力が必要になる
- **対策**：最初から全部の本を入力する必要はなく、自分のペースで登録してもらう。入力しているうちに「積んでる本、多いな」と気づいてもらえるだけでも価値がある
- **確かめたいこと**：登録の途中でやめた人が、再び戻ってくるか

### 懸念3：自覚のない人は、アプリに出会えない

- **なぜそう思うか**：自分が書籍コレクターだと認識していない人には、アプリを探すきっかけも、使う理由もない
- **対策**：まずは同じスクールの受講生に使ってもらい、このサービスに価値があるかを調査する

### 懸念4：「周りの受講生も同じ悩みを感じているか」が、まだ想定にとどまる

- **なぜそう思うか**：課題はあなた自身の体験が出発点で、周りの受講生が同じ悩みを感じているかは未確認
- **対策**：作ってから、受講生に使ってもらい、感想を聞く
- **リリース後に確かめたいこと（案）**：
  - 登録した冊数と、そのうち「積んでる」の割合
  - 登録して、積んでいる本が多いことに気づいたか
  - その後、本を買うのをやめたり、迷ったりしたか

## 10. 技術スタック

### 10-1. 使用予定の技術

| 項目 | 内容 |
| --- | --- |
| フレームワーク | Ruby on Rails |
| DB | PostgreSQL（Renderの有料プラン） |
| デプロイ先 | Render |
| ライブラリ | Devise（ユーザー認証） |

### 10-2. 技術選定の比較検討

| 項目 | 候補 | 採用/不採用 | 理由 |
| --- | --- | --- | --- |
| フレームワーク | Ruby on Rails | 採用 | Railsの学習の一環として作るため（他のフレームワークは比較していない） |
| DB | PostgreSQL（Render有料） | 採用 | サービスとして公開する以上、本番相当のDBを使いたい |
| DB | Renderの無料PostgreSQL | 不採用 | 期限があり、期限後はデータが削除されるため、公開サービスに向かない |
| 認証 | Devise | 採用 | 認証を自前で作らず、ライブラリに任せる |
| デプロイ先 | Render | 採用 | 他のサービスとは比較していない |

> ※有料プランの費用は、Render公式の料金ページで確認する（要確認）。
> ※アプリ本体（Webサービス）のプランは未定。無料プランは一定時間アクセスがないと停止し、次のアクセス時に起動し直すため、初回表示が遅くなる。受講生に使ってもらう段階で、気になるか確かめる。

**今回チャレンジしたい点**：ユーザー認証の実装、本番環境へのデプロイ、実際のユーザーに使ってもらうこと

**不安な点**：継続をサポートする機能が弱い
（7で、計画の後押しなどを意図的に作らないと決めたことによるトレードオフ。8の対策のとおり、早くリリースして使ってもらい、感想を聞いて確かめる。弱いと分かった場合は、軸を保てる範囲で何を足すかを検討する）

### 10-3. キャッチアップ不足の懸念

自作アプリの開発自体が初めてで、Ruby on Rails、Devise、PostgreSQL、Renderへのデプロイは、すべて学習中。MVPに入れた機能がすべて初めての技術なので、完成までのハードルが高くなることと、Issueの見積もりが難しくなることが懸念される。

そこで、**段階的に取り入れる**。各段階で動くものができるので、Issueも切りやすくなる。

| 段階 | 内容 | 新しく触れる技術 |
| --- | --- | --- |
| 1 | 本の登録と一覧（ログインなし、ローカルで動かす） | Rails、PostgreSQL |
| 2 | アカウント登録とログインを足す | Devise |
| 3 | Renderにデプロイして、URLを公開する | Render |
